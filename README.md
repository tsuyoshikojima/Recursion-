# RecursionCS 学習・プロジェクト実践ガイド

**目的：CSの基礎を理解し、バックエンド開発に応用し、AIを活用しながら品質に責任を持てるようになる。**  
**適用範囲：** RecursionCSの概念学習、コーディング課題、チュートリアル、個人・チームプロジェクト。  
**基本姿勢：** 完璧なノートや豪華なリポジトリを作ることではなく、「理解・実装・検証・説明」を積み上げる。

## 1. 学習の4原則

1. **学習対象の核心は自分で考える。** アルゴリズム、データ構造、OOP、並行処理、HTTP、DB、認証・認可、設計判断は思考をAIに丸投げしない。
2. **AIは家庭教師兼レビュー担当として使う。** 分からない箇所の説明、比較、ヒント、理解度テスト、レビューに活用する。
3. **開発ではAIに任せる範囲を広げる。** 定型コード、環境設定の補助、テスト案、ドキュメント整備などを効率化する。ただし生成結果は検証する。
4. **作業量より説明可能性を重視する。** 「なぜこの設計なのか」「どう失敗するか」「どう確かめたか」を自分の言葉で答えられる状態を目指す。

## 2. 学習形式ごとの進め方

| 形式 | 主な目的 | 自分で行うこと | AIに任せてよいこと |
| --- | --- | --- | --- |
| 概念・理論の教材 | 原理と必要性の理解 | 読み、図解し、言葉で説明する | 別の説明、比較、確認問題 |
| コーディング課題 | 思考力・実装力の獲得 | 方針、実装、手動テスト、計算量の説明 | 段階的ヒント、反例、コードレビュー |
| チュートリアル | 技術を使う一連の流れの体験 | コードを動かし、変更し、挙動を説明する | 環境の補助、詰まりの解消、理解度確認 |
| プロジェクト | 要件から完成までの開発 | 仕様・重要な設計判断・動作検証 | 定型実装、設計レビュー、テスト・文書支援 |

## 3. 1レッスンの標準フロー

**① 全体をつかむ（2〜5分）**：見出しと到達目標を確認し、「何ができるようになる教材か」を一文にする。

**② 自分で読む・考える**：まず原文を読む。分からない語は一旦印を付け、主題を見失わない。すべての周辺知識をその場で深掘りしない。

**③ 必要な箇所だけAIに質問する**：「何か」「なぜ必要か」「使わないと何が起こるか」「関連技術との違い」を優先する。説明を受けたら自分の言葉で言い換える。

**④ 小さく試す**：サンプルを実行し、入力・条件・実装を1つだけ変更して結果を予想する。予想と異なれば理由を調べる。

**⑤ 思い出して説明する（2〜3分）**：教材を見ずに「目的・仕組み・使いどころ」を説明する。重要な単元ではAIに1〜3問出してもらう。

**⑥ 最小限の記録を残して進む**：学んだことを1〜3行、疑問を必要なら1行だけ記す。理解不足は「再訪リスト」に回す。

**停止ルール：** 15〜20分悩んで進展がなければ、現状・期待結果・試したこと・エラー全文をAIに渡してヒントを得る。回答を読むだけで終わらせず、もう一度自分で再現する。

## 4. 分野別に重視するポイント

| 分野 | 押さえるべき観点 | 小さな確認方法 |
| --- | --- | --- |
| アルゴリズム・データ構造 | 不変条件、計算量、境界条件、選択理由 | 手計算→実装→反例・テスト |
| OOP・設計 | 責務、依存関係、カプセル化、変更容易性 | クラスの責務を一文で説明する |
| OS・ネットワーク・並行処理 | データや処理の流れ、状態、競合、失敗 | 時系列図、通信ログ、再現実験 |
| フロントエンド | 状態、イベント、非同期処理、表示の更新 | 入力→状態変更→再描画を追う |
| バックエンド・API | HTTP、検証、エラー、認証、責務分担 | リクエストからレスポンスまで追う |
| DB | スキーマ、制約、トランザクション、インデックス | SQLを実行し結果と実行計画を確かめる |
| テスト・セキュリティ | 失敗ケース、境界、権限、秘密情報 | 異常入力と権限外操作を試す |

細かなAPI名やコマンドの暗記より、仕組みと設計上の理由を優先する。一方、頻出の基本構文・SQL・Git操作は反復して身につける。

## 5. コーディング課題でのAI利用ルール

**原則：最初の解法をAIに出させない。** まず問題を分解し、入出力、制約、方針、計算量を考える。

1. **自力で着手**：例を手で追い、擬似コードや簡単な方針を書く。
2. **行き詰まったらヒント**：「答えやコードは出さず、次の一歩だけ示して」と頼む。
3. **実装後にテスト**：正常系、空、最小・最大、重複、不正入力など、問題の仕様に合うケースを確認する。
4. **最後にレビュー**：正しさ、計算量、読みやすさ、別解をAIと比較する。
5. **再実装できるか確認**：解説を見ずに核心部分を書けるか、なぜ動くか説明できるかを確かめる。

アルゴリズム課題ではAI生成の完成解答を早い段階で読まない。学習目的が薄い定型処理に限り、実装を任せてもよい。

## 6. プロジェクトの標準開発フロー

### Phase 0｜目的と完成条件を決める

まず「何を作り、どこまでできたら完成か」を定める。MVP（最小実用機能）を決め、追加機能は後回しにする。

- **目的**：誰の、どの問題を解決するのか。
- **主要機能**：必須機能を3〜5個程度に絞る。
- **制約**：言語・フレームワーク・保存方式・実行環境・締切。
- **受け入れ条件**：「○○すると△△になる」と観察可能な形で書く。
- **対象外**：初版では作らないものを明記する。

### Phase 1｜最小限の設計を自分で考える

外部とのインターフェース、主要な処理の流れ、データ構造・DB、モジュールの責務、想定する失敗を考える。設計図は必要な場合だけ作り、最初から大規模なアーキテクチャにしない。

**AIの役割：** 自分の案に対して「責務の混在」「不要な抽象化」「障害時の問題」「見落とした仕様」を指摘させる。最終判断は自分で行い、理由を残す。

### Phase 2｜小さな単位に分ける

動作を確認できる縦方向の機能単位で分割する。たとえば「APIの入力→バリデーション→処理→レスポンス→テスト」を一つ通す。Issueは作業を管理するのに役立つときに使い、細かすぎるチケットは増やさない。

### Phase 3｜機能ごとに実装・検証する

**1機能のループ：** 要件確認 → 自分で方針を考える → 必要な部分をAIに依頼 → 差分確認 → 実行・テスト → コミット。

**自分主体にする部分：** 重要な処理のロジック、状態管理、DB設計、認証・認可、APIの振る舞い、並行処理など、学習上の核心。

**AIを積極活用する部分：** ボイラープレート、設定手順、入力バリデーションの叩き台、テストケース案、リファクタリング案、READMEの下書き。ただし認証・セキュリティ関連の生成コードは重点的に検証する。

### Phase 4｜品質を確かめる

正常系だけでなく、不正入力、異常系、境界条件、連続リクエスト、必要に応じた並行処理を確認する。テストを書いて実行し、結果を記録する。AIのレビューは補助であり、テスト成功の代わりにはならない。

### Phase 5｜説明できる状態で完成させる

READMEに「目的、機能、技術、起動方法、使い方、テスト実行方法、主な設計判断、既知の制約」をまとめる。デモができ、主要な設計・トレードオフを説明できれば一区切りとする。

## 7. AIエージェント利用時の実務ルール

- **作業範囲を限定する**：「まず方針のみ」「このファイル群だけ」「1機能のみ」など、変更範囲と完了条件を伝える。
- **既存実装を尊重させる**：勝手な全面書き換えや不要な依存ライブラリの導入を避ける。
- **差分を読む**：`git diff`で変更箇所を確認し、意図しない削除、過剰な抽象化、例外の握りつぶしがないか見る。
- **実行結果で検証する**：テスト、手動操作、ログ、入力例で確認する。「AIが大丈夫と言った」は根拠にしない。
- **秘密情報を渡さない**：APIキー、トークン、パスワード、個人データをプロンプトやGitに入れない。`.env`などは`.gitignore`に追加する。
- **破壊的操作を承認前に確認する**：ファイル削除、DB破棄、権限変更、外部公開、費用を伴うAPI利用は特に注意する。

**レビュー時の自問：** この変更の目的は何か／入力と出力は何か／どこで失敗するか／なぜこの分割か／どうテストしたか。

## 8. Git・リポジトリ・ドキュメントの運用

**Git：** 機能が一段階動いたらコミットする。単独開発では無理に複雑なブランチ運用をしなくてよい。変更範囲が大きいときは機能ブランチやPull Requestを利用する。

コミットメッセージ例：`feat: add upload endpoint`、`test: cover invalid inputs`、`docs: explain local setup`。

**最小構成の例（言語・フレームワークに合わせて変更する）：**

```text
project/
├── src/            # 実装。Laravel等では標準構成に従う
├── tests/          # 自動テスト
├── README.md       # 使い方と全体像
└── .gitignore      # 秘密情報・生成物を除外
```

**READMEを先に整え、`docs/`は必要になってから追加する。** 仕様が複雑になったときだけAPI仕様・設計メモ・図を残す。学習メモとプロジェクトの正式ドキュメントは分けると管理しやすい。

**残す価値がある記録：** なぜ選んだか、何と比較したか、何を検証したか、既知の制約は何か。AIで大量の文書を作ること自体を目的にしない。

## 9. コースとプロジェクトの完了基準

| 対象 | 完了と判断する条件 |
| --- | --- |
| 概念レッスン | 目的・基本原理・代表的な使いどころを説明できる |
| コーディング課題 | 自力で筋道を説明でき、主要な境界ケースで正しく動く |
| チュートリアル | サンプルを動かし、重要部分を一つ変更して挙動を説明できる |
| 学習プロジェクト | 必須機能が動き、テストし、重要な設計を説明できる |
| 転職用ポートフォリオ | 上記に加え、セットアップ再現性、エラー処理、README、代表的テスト、設計判断の説明がある |

完璧を追い続けず、次のコースへ進む。**未解決の疑問は記録し、実際の開発で必要になったときに再訪する。** ただし安全性やデータ破壊に関わる問題は放置しない。

## 10. バックエンド学習での重点配分

**P4など基礎実装が中心の段階：** OOP、関数設計、データ構造、例外処理、I/Oは自力実装を多めにする。AIはヒント・レビュー担当に寄せる。

**P5などアプリ開発・設計が中心の段階：** 要件分解、API・DB設計、認証、テストに思考時間を使い、定型処理はAIに補助させる。Laravelなどフレームワークの標準構成を優先し、独自の階層を不必要に増やさない。

**転職を意識する段階：** 1つのプロジェクトを、動作・品質・説明可能性の3点で深める。数多くの未完成プロジェクトを作るより、README、テスト、設計理由を示せる完成品を優先する。

学習時間が限られる場合は、まず主要コースと必須プロジェクトの進捗を優先し、過剰なUI調整・ツール比較・文書整備に時間を使いすぎない。

## 11. すぐに使えるAIプロンプト

**教材の理解：** 「次の教材について、まず重要概念を3つ挙げ、それぞれ『何か・なぜ必要か・どこで使うか』で説明してください。教材にない推測は区別してください。」

**ヒントのみ：** 「この課題は自力で解きたいです。完成コードは示さず、私の方針の問題点と次の一歩だけ教えてください。」

**理解度確認：** 「この単元から、暗記ではなく仕組みと設計理由を問う問題を3問、1問ずつ出してください。私の回答後に採点してください。」

**設計レビュー：** 「この要件と私の設計案をレビューしてください。責務の分離、代替案、トレードオフ、見落としを指摘し、まだコードは変更しないでください。」

**変更レビュー：** 「この差分について、仕様との不一致、バグ、セキュリティ、テスト不足、不要な複雑化を優先度順に指摘してください。根拠と確認方法も示してください。」

**ドキュメント：** 「現在の実装に基づきREADMEの下書きを作ってください。コードから確認できない事項は推測で補わず『要確認』にしてください。」

## 12. 毎回のチェックリスト

### レッスン終了時

- [ ] この技術の目的を説明できる
- [ ] 基本的な動作・仕組みを理解している
- [ ] 代表例を動かす、または自力で説明できる
- [ ] 不明点を必要な範囲で整理した
- [ ] 次へ進むか、再訪するかを決めた

### プロジェクトの機能完成時

- [ ] 受け入れ条件を満たしている
- [ ] AIの変更差分を確認した
- [ ] 正常系・異常系・境界ケースを検証した
- [ ] 秘密情報・権限・エラー処理を確認した
- [ ] コミットし、必要なドキュメントを更新した
- [ ] 実装・設計判断を自分で説明できる

---

**最終指針：** チュートリアルではAIを「家庭教師」として、プロジェクトでは「開発アシスタント」として使う。学習の核心は自分で考え、定型作業は効率化し、生成された成果物は必ず検証する。目指すのは「AIを使わず全部書ける人」でも「AIに全部作らせる人」でもなく、**技術を理解し、道具を使い、品質を判断できるエンジニア**である。
